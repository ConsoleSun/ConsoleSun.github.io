企业级 AI Agent 框架实践:外贸智能体系统

发表于2026-08-02|更新于2026-08-06|技术
|浏览量:

这不是一篇”Hello World”级别的 Agent 教程,而是一个真正跑在生产环境的外贸智能体系统的框架拆解。它同时服务外部客户(产品咨询、以图搜图)和内部员工(知识检索、邮件收发、客户挖掘、ERP 同步),并且已经实现了全自动获客。

一、为什么做这件事

公司在做玻璃瓶制造与出口。外贸业务有两个很真实的痛点:

对客户——一个德国客户问”丘比特瓶子的规格是什么”,一个中东客户把酒瓶照片甩过来问”这个能做吗”。他们不想翻几十页的产品手册,就想有人能立刻答上来。

对员工——业务员要查报价、查工艺、查管理制度,发开发信、跟客户、把客户录进 ERP。信息散在四五个系统里,操作步骤繁琐,新人上手尤其慢。

我最初的想法很简单:能不能把这些全塞进一个对话框里? 客户和员工都只对着一个”人”说话,背后由 Agent 去查知识库、上网、发邮件、写 ERP。于是有了这个系统。

二、核心设计理念

LLM 是大脑(推理决策),上下文是眼睛(它能看到什么),工具是手脚(它能做什么)。框架层的绝大多数工作,都是在打磨这三者的边界和配合。下面讲到的每个机制,本质都是在回答一个问题:如何让一个不完美的大脑,在一个不可控的环境里,稳定地办成事。

三、七层架构

七层各司其职,前后端完全解耦。核心技术资产集中在第⑤层,下面重点讲。

四、一颗会”察言观色”的大脑:视角状态机

同一个模型,要同时面对客户和内部员工,还要写开发信。语气和检索策略完全不同——同样问”玻璃瓶”,客户要的是产品介绍,员工要的是内部工艺参数。

系统用了一个轻量级状态机,管理三种视角:

状态 触发场景 效果
CUSTOMER_FACING_COMM 开发信、报价谈判、客户邮件 优先搜业务/开发信库,外贸销售口吻
INTERNAL_OPERATIONAL 生产工艺、制度查询 优先搜管理/技术库,内部口吻
NEUTRAL 日常问候、通用推理 等权搜索所有库

三个有意思的细节:

1. 防抖(Debounce)——对话聊到一半,状态机不会轻易”跳戏”。NEUTRAL 状态下如果已有强上下文约束,就保持当前视角,避免在几轮对话里反复横跳。代码里叫”弱锁定机制”:只有从强状态往中立退时才加限制,该切的时候照样切。

2. 近因效应注入(Recency Bias Tail Injection)——大模型对上下文末尾的内容最敏感。状态机根据当前视角,在消息末尾动态注入一段行为引导:”当前对话已判定为对外客户沟通视角,请采用外贸资深销售顾问口吻,注重商业礼仪与谈判切入点,严禁直接堆砌内部规章表格。” 用很小的 token 成本,把模型的”人设”掰到正确位置。

3. RAG 权重分配——不同视角下,四个知识库的检索优先级权重动态调整(0.5×~1.5×)。对外视角时 search_outreach(8000+封爆款开发信库)权重拉到 1.5,内部视角时 search_mgmt 拉到 1.5。

五、上下文四层结构:Agent 的”视野”

代码注释里写着这么一句话:“这是全书最重要的一个模块——上下文质量直接决定 Agent 能力上限。”

一个工程细节:为了最大化 DeepSeek 上下文缓存的命中率,系统把一切动态内容(时间戳、澄清引导、视角引导)统一折进用户消息末尾,让 system 前缀保持恒定。这样同一段前缀在 DeepSeek 的 KV 缓存里全程命中,代价只是毫秒级的检索,速度提升非常明显。缓存命中的收益是实打实的。

六、两个身份,两套 Prompt

同一个 Agent 框架,给客户和员工配了完全不同的 System Prompt。这值得单独拿出来讲,因为”人味”全在这里面。

给客户的 Prompt 写的是:

你是 Valiant Glass 的外贸客服助手……回复风格:专业但友好,像一个有经验的销售顾问……涉及规格参数时给出具体数字,避免模糊描述……用客户提问的语言回复(中文客户用中文,英文客户用英文)。

给员工的 Prompt 写的是:

你是 Valiant Glass 的内部业务助手……回复风格:高效、准确……涉及制度流程时,给出具体条款和出处,技术参数用表格呈现,便于对比。

两者还有共同的铁律:

  • 工具优先:用户给了核心关键词(国家/产品名/SKU)就必须立即调工具,严禁死循环追问。比如员工回”埃及,酒瓶”,Agent 立刻 lead_mining(keyword="glass bottle manufacturer", country="Egypt")。
  • 禁止编造:所有知识库检索结果为空时,必须诚实告知”知识库暂未收录”,绝不允许用通用知识冒充公司内部信息。这条约束直接决定了回答的可信度。
  • 边界分明:对客户禁止透露内部管理制度、人事信息、成本价;禁止执行任何写操作,下单退款一律引导联系人工销售。

“人味”不是靠堆辞藻,而是靠把语气、立场、边界都写进 Prompt,让模型在每次回答时都知道自己是谁、该怎么说、什么不能说。

七、工具网关:一条 5 步管线

工具调用是 Agent 落地最脆弱的环节。每次调用都走同一条 5 步管线:

  • 熔断(breaker.py):全局连续 3 次失败 → 60 秒冷却,防止雪崩。
  • 权限(permissions.py):三级 RBAC(customer 5 个工具 / staff 18 个 / admin 18 个)+ 参数级规则。客户永远调不到 send_email。
  • 执行(gateway.py):从注册表取工具 spec,调用异步执行函数。工具用 @tool() 装饰器声明,天然可注册、可发现。
  • 校验(validators.py):每个工具配独立校验器,检测空结果/错误/异常。
  • 修正(gateway.py::_correct()):校验失败 → 生成纠偏上下文反馈给 LLM,让它换一种方式重试(同工具最多 2 次)。

这一条管线,把”工具可能失败、结果可能不可信”这件事,变成了有护栏、有重试、有降级的确定性流程。

八、安全:五面防御

生产环境的 Agent 最怕两件事:被人诱导越权 和 幻觉乱说。

  1. 输入安全:20+ 条正则检测提示注入(中英文覆盖),拦截角色标签注入、越狱模式、指令覆盖。
  2. 输出安全:正则检测 API Key 泄露、内网 IP 泄露、内部价格泄露;外加可选的 LLM 二次幻觉校验(检测编造 SKU、虚构报价)。
  3. 工具安全:SSRF 防护(web_fetch 阻止内网/本地地址)、路径穿越防护(save_file 和图纸代理均做路径校验)、文件大小限制。
  4. 认证鉴权:JWT access + refresh 双令牌(刷新一次性轮转)、API Key bcrypt 哈希存储、三级 RBAC。
  5. 速率限制:Redis 滑动窗口(默认 10 次/分钟)+ 日配额(200 次/天)。

九、可观测性与评估:不能盲人骑瞎马

  • Trace 追踪:每个请求生成一条结构化 JSONL 日志,记录 trace_id、llm_calls、tool_calls、每步耗时 span。线上排查 Agent 行为全靠它。
  • 评估框架(agent/eval/):LLM-as-Judge 从 4 个维度打分——关键词覆盖度、幻觉检测(保守原则,宁可漏判不误判)、澄清检测、综合评分。测试集跑完生成 Markdown 报告,与 baseline.json 对比做回归。

没有评估框架的 Agent 系统等于盲人骑瞎马。哪怕是一个 4 维的粗粒度打分,也能让你在改 prompt、改工具后立刻知道是变好还是变坏。

十、全自动获客:一键跑完整个外贸链路

这是系统里最能体现”工具链编排”价值的场景:

工程细节:

  • 去重:Redis SET 记录所有已联系邮箱/域名,跨国家重复公司不重发。
  • 进度流独立存储:campaign 进度放独立 Redis store,绝不进入 LLM 上下文,防止获客过程污染对话。
  • 可停止可恢复:每个用户一个后台 task,随时可停,重启可续。

十一、测试:200+ 用例守住底线

  • 三层测试集:单元测试(纯逻辑 + mock 外部依赖)/ 存储层(fakeredis)/ API(TestClient + 依赖注入),约 200+ 用例。
  • 测试不需要真实 Redis / PostgreSQL / LLM / 浏览器 / 邮件服务器——Redis 用 fakeredis,其余全部 mock。这保证了 CI 每次 push 都能快速跑完。
  • 还有一组真实环境 E2E 用例(真实 Google Places / 公司 ERP / DeepSeek),默认排除,需要显式运行——避免 CI 里消耗配额、写脏测试记录。

十二、待更新项

系统已经跑通了”获客 → 联系 → 转化”的大部分链路。下一步有三个方向,目标是把全流程的最后一公里补完,从获客到归档实现全自动化:

1. 全流程信息跟踪

将发送和接收的客户邮件全部存储,并把邮件中的信息结构转化为图向量。当用户收到客户回信时,LLM 同步检索 RAG 中该客户的向量块,把历史所有来往信件汇总展示。

用户可以二选一:

  • LLM 自动综合回复——基于全部往来历史自动起草一封回信;
  • 人工回复——把历史脉络摊开给业务员,让他自己写。

一句话:让每一封邮件都成为可被检索、可被关联的记忆,而不是躺在收件箱里的孤岛。

2. 复杂任务转交

当 LLM 识别到两种情形时,调用工具主动通知业务员:

  • 客户意图是要和真人业务员沟通;
  • 或任务过于复杂、Agent 无法完成。

通知方式包括邮件、电话、钉钉等。核心是让 Agent 学会”什么时候该放手”——不是硬撑到失败,而是识别到自己的能力边界,把接力棒交给人类。

3. Agent 自进化

数据库中每产生一条成交记录,LLM 就会对该记录做一次归档,包括但不限于:

  • 国家/地区、行业、来源;
  • 来往信件的写作风格、促成成交的关键话术。

归档分两种形式,双管齐下:

  • Markdown 文档,用于动态注入上下文,让 Agent 在后续对话中自然带上”这个市场怎么聊”的经验;
  • 同时写入 RAG,让历史成交经验可以被检索复用。

至此,这个 Agent 从获客到归档的全流程自动化正式打通:获客、联系、转化、复盘,每一步的经验都沉淀下来,成为下一步的养料。

十三、工程经验小结

  1. 把”动态”和”静态”分离:System Prompt 保持恒定以命中上下文缓存,动态内容全进用户消息末尾——一次改动,速度肉眼可见提升。
  2. Agent 的安全必须做成管线,而不是散落的 if:5 步网关让每个新工具自动获得熔断、权限、校验能力。
  3. 状态机比”一股脑灌上下文”更优雅:视角 FSM 用很小的代价让同一个模型适配了两种截然不同的用户。
  4. 能交给确定性逻辑的就别让 LLM 干:去重用 Redis、限速用滑动窗口、幻觉检测兜底用正则先行——LLM 只做它擅长的事。

结语

这套框架最有价值的地方,不是某个单点技术,而是把 LLM 的不确定性 用工程手段约束起来:上下文怎么给、工具怎么调用、失败怎么修正、输出怎么过滤、质量怎么评估——每个环节都有明确的设计。

AI Agent 的落地,拼的不是模型的智商,而是框架对边界的定义和兜底能力。而下一步,是让它在真实业务里不断沉淀、自我进化。
