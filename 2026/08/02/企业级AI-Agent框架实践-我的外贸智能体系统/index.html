企业级 AI Agent 框架实践:我的外贸智能体系统

发表于2026-08-02|更新于2026-08-02|技术
|浏览量:

这不是一篇”Hello World”级别的 Agent 教程,而是一个真正跑在生产环境的外贸智能体系统的框架拆解。它同时服务外部客户(产品咨询、以图搜图)和内部员工(知识检索、邮件收发、客户挖掘、ERP 同步),并实现了全自动获客。

一、项目背景

公司是一家玻璃瓶制造与出口企业(Valiant Glass)。业务上有两类典型诉求:

  • 外部客户:想查”丘比特瓶子的规格””这款酒瓶有没有现货”,甚至直接发一张图纸问”能不能做”。
  • 内部员工:要查产品报价、生产工艺、管理制度,要发开发信、跟进客户、把客户同步进 ERP。

传统做法是给业务人员配一堆系统 + 知识库,但知识分散、操作割裂。我做的这个系统用一个 Agent 统一承载两类场景,把知识检索、联网、邮件、ERP、视觉搜索全部收敛成”对话”这一种交互。

二、核心设计理念

这是整个系统的出发点。LLM 是大脑(推理决策),上下文是眼睛(它能看到什么),工具是手脚(它能做什么)。框架层的绝大多数工作,都是在把这三者的边界和配合打磨好。

三、七层架构

七层各司其职,前后端可以完全解耦开发。核心技术资产集中在第⑤层,下面重点讲。

四、Agent 核心层的四个关键机制

1. ReAct 循环(agent/loop.py)

循环结构并不新奇:LLM 决策 → 执行工具 → 结果喂回 → 再决策。但实现上有两个工程化细节:

  • 意图澄清预检:首轮先用一次轻量级 LLM 调用判断消息是否模糊。明确的(“VIT-001 的规格”)直接进入 ReAct;模糊的(“帮我查一下”)先返回一个精准的澄清提问,避免 Agent 在错误方向上白白消耗步数。
  • 最大步数护栏:默认 5 步封顶,防止 Agent 陷入循环烧 token。

2. 上下文四层结构(harness/context.py)

上下文怎么组织,直接决定 Agent 的表现:

值得一提的工程细节:为了最大化 DeepSeek 的上下文缓存命中率,系统把动态内容(时间戳、澄清引导、视角引导)统一折进用户消息末尾,让 system 前缀保持恒定。结果是缓存全程命中,速度显著提升。

3. 视角状态机(harness/perspective_fsm.py)

这是我觉得最有意思的设计。同一个 Agent 要面对客户和内部员工两类人,回答口吻、检索的库都该不一样。系统用一个轻量的状态机管理三种视角:

状态 触发场景 效果
CUSTOMER_FACING_COMM 开发信、报价谈判、客户邮件 优先搜业务/开发信库,外贸销售口吻
INTERNAL_OPERATIONAL 生产工艺、制度查询 优先搜管理/技术库,内部口吻
NEUTRAL 日常问候、通用推理 等权搜索所有库

三个关键机制:

  • 防抖(Debounce):NEUTRAL 状态下若已有上下文约束,不轻易退回上一状态,避免视角在几轮对话里反复横跳。
  • Recency Bias Tail Injection:根据当前状态在上下文末尾动态注入行为引导——利用大模型对”末尾内容”更敏感的特性。
  • RAG 权重分配:不同视角下动态调整 4 个知识库的检索优先级权重(0.5×~1.5×)。

每个会话维护独立的 FSM 实例,状态跨轮次保持,配合有界的空闲淘汰策略防止内存无限增长。

4. 工具网关五步管线(agent/gateway/)

这是系统的”安全阀”。每次工具调用都走同一条 5 步管线:

  • 熔断(breaker.py):全局连续 3 次失败 → 60s 冷却,防止雪崩。
  • 权限(permissions.py):三级 RBAC(customer 5 个工具 / staff 13 个 / admin 13 个)+ 参数级规则。比如客户永远调不到 send_email。
  • 执行(gateway.py):从注册表取工具 spec,调用异步执行函数。工具用 @tool() 装饰器声明,天然可注册、可发现。
  • 校验(validators.py):每个工具配独立校验器,检测空结果/错误/异常。
  • 修正(gateway.py::_correct()):校验失败 → 生成纠偏上下文反馈给 LLM,让它换一种方式重试(同工具最多 2 次)。

这一条管线解决了 Agent 落地最常见的痛点:工具不可靠、结果不可信、失败不可控。

五、安全设计:五面防御

生产环境的 Agent 最怕两件事:被人诱导越权 和 幻觉乱说。系统在 5 个面做了防御:

  1. 输入安全:20+ 条正则检测提示注入(中英文覆盖),拦截角色标签注入、越狱模式、指令覆盖。
  2. 输出安全:正则检测 API Key 泄露、内网 IP 泄露、内部价格泄露;外加可选的 LLM 二次幻觉校验(检测编造 SKU、虚构报价)。
  3. 工具安全:SSRF 防护(web_fetch 阻止内网/本地地址)、路径穿越防护(save_file 和图纸代理均做路径校验)、文件大小限制。
  4. 认证鉴权:JWT access + refresh 双令牌(刷新一次性轮转)、API Key bcrypt 哈希存储、三级 RBAC。
  5. 速率限制:Redis 滑动窗口(默认 10 次/分钟)+ 日配额(200 次/天)。

六、可观测性与评估

  • Trace 追踪:每个请求生成一条结构化 JSONL 日志,记录 trace_id、llm_calls、tool_calls、每步耗时 span。线上排查 Agent 行为靠的就是它。
  • 评估框架(agent/eval/):LLM-as-Judge 从 4 个维度打分——关键词覆盖度、幻觉检测(保守原则,宁可漏判不误判)、澄清检测、综合评分。测试集跑完后生成 Markdown 报告,和 baseline.json 对比做回归。

Agent 系统没有评估框架 = 盲人骑瞎马。哪怕是一个 4 维的粗粒度打分,也能让你在改 prompt、改工具后立刻知道是变好还是变坏。

七、特色功能:全自动获客(Auto Campaign)

这是系统里最能体现”工具链编排”价值的场景:

几个工程细节:

  • 去重:Redis SET 记录所有已联系邮箱/域名,跨国家重复公司不重发。
  • 进度流独立存储:campaign 进度放独立 Redis store,绝不进入 LLM 上下文,防止获客过程污染对话。
  • 可停止可恢复:每个用户一个后台 task,随时可停。

八、工程经验小结

  1. 把”动态”和”静态”分离:System Prompt 保持恒定以命中上下文缓存,动态内容全进用户消息末尾——一次改动,速度肉眼可见提升。
  2. Agent 的安全必须做成管线,而不是散落的 if:5 步网关让每个新工具自动获得熔断、权限、校验能力。
  3. 状态机比”一股脑灌上下文”更优雅:视角 FSM 用很小的代价让同一个模型适配了两种截然不同的用户。
  4. 能交给确定性逻辑的就别让 LLM 干:去重用 Redis、限速用滑动窗口、幻觉检测兜底用正则先行——LLM 只做它擅长的事。

结语

这套框架最有价值的地方,不是某个单点技术,而是把 LLM 的不确定性 用工程手段约束起来:上下文怎么给、工具怎么调用、失败怎么修正、输出怎么过滤、质量怎么评估——每个环节都有明确的设计。

AI Agent 的落地,拼的不是模型的智商,而是框架对边界的定义和兜底能力。
