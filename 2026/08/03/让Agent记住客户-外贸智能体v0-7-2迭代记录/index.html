让 Agent 记住客户:外贸智能体 v0.7.2 迭代记录

发表于2026-08-03|更新于2026-08-06|技术
|浏览量:

这是上一篇《企业级 AI Agent 框架实践:外贸智能体系统》的迭代续篇。那篇讲的是整体框架,这篇讲的是 v0.7.2 一次真实的版本迭代:客户记忆系统、滚动对话摘要、获客性能优化、发信策略收紧。它记录的不是”我又写了什么”,而是”我为什么这么写”。

一、这次迭代最想解决的一个问题

做外贸,最珍贵的信息藏在客户的话里:

“我们需要 500ml 高白料伏特加瓶,年需求 20 万只,要配 T 型木塞。”

客户今天说完这句,可能三个月后才回来问”上次那款还能做吗”。如果 Agent 什么都不记得,他得重新讲一遍——每一次都像第一次,这是跟单里最伤体验的事。

所以 v0.7.2 的第一个目标很明确:让 Agent 跨会话记住客户的核心需求。

二、客户记忆系统:零额外 LLM 调用的沉淀方案

记忆怎么落下来

系统的意图预检,本来就是一次轻量级 LLM 调用(同时做澄清检测 + 视角分类)。这次迭代让它顺带多输出一个 important_memory_note:

  • 识别客户本轮消息里的核心业务需求(瓶型、容量、材质、采购量、目标价、目的港、定制工艺、测试要求)
  • 提炼成一句高度精炼的话,带时间戳增量追加进 PostgreSQL 的 customer_memory 表
  • 纯招呼/闲聊/无新需求 → 设为 null,不写

没有新增任何一次 LLM 调用,复用还是那一次预检。 记忆是”顺水推舟”沉淀下来的,而不是额外付出成本。

记忆怎么被用起来

新增了一个 get_customer_memory 工具,三种查询方式:

方式 用法 场景
按邮箱精确查 email=buyer@brand.com 跟进某个具体客户
按关键词全文检索 keyword=伏特加瓶 找出所有提过该需求的客户
列出全部 都不传 全量档案速览

注入策略也做了分层:

  • 客户侧:双层有界注入——最近 8 条 + 即时检索更早的记录
  • 员工侧:注入最近活跃客户记忆索引,触发 Agent 主动回唤 get_customer_memory

所有注入都压在消息末尾,不破坏 KV 缓存前缀。

安全隔离:这块是真正的亮点

记忆系统最容易被做砸的地方,是跨客户泄露。这里有一个很多人会踩的坑:

所有匿名外部客户共用同一个系统账号。如果拿这个账号当记忆主键,客户 A 的需求就会泄露给客户 B。

我用了 email → user → session 三档降级主键,并且在代码里识别出共享系统账号,跳过 user 档,直接降到 session 级隔离——每个匿名会话的记忆互相隔离。客户一旦留下邮箱,再把 session 记忆融合迁移成永久的 email 键,记忆跟着客户走,而不是跟着会话走。

查询侧同样做了隔离:关键词检索只搜 email:% 永久键,显式排除内部 user 键(会泄露其他员工的跟进备注)和临时 session 键。

再加最后一道:工具网关层 role_in(["staff","admin"]) 权限——客户角色在工具层就调不到这个工具,连尝试的机会都没有。

记忆的”物理隔离”在代码里,不在提示词里。

三、滚动对话摘要:长对话的解法

v0.7.1 之前,历史超过 20 轮会被硬切。硬切有个隐患:第 3 轮说过的一个关键规格,如果第 21 轮还要用,它已经没了。

v0.7.2 的做法是滚动摘要:

  • 历史超过 CONVERSATION_MAX_TURNS(默认 20)后,窗口外最老的一段折叠进摘要,再裁剪历史
  • 摘要由 LLM 合并生成,≤250 字,只保留要点
  • 摘要只在折叠时更新(每 N 轮一次),非逐轮动态 → 前缀保持恒定,KV 缓存不破

这把”超长对话会丢关键信息”的隐患,从”裁掉”变成了”压缩进摘要”。代价是每折叠一次多一次 LLM 调用,换来的是长任务不丢上下文。

四、获客性能优化:每封邮件 40s → 25s

全自动获客这条流水线,之前的瓶颈在于串行:挖完一家,写一封,发一封,同步 ERP,再来下一家。v0.7.2 改成流水线:

  • 挖掘并发(默认 2):同时挖多个客户
  • 批量并发起草(批量 5、并发 4):多封开发信同时由 LLM 起草
  • 生产-消费流水线:把挖掘、起草、ERP 同步的时间藏进发送间隔(限速的等待时间不再空转)
  • ERP 异步化:写 ERP 不阻塞发信流程

结果:每封邮件的墙钟时间从 ~40s 降到 ~25s,提速约 37%。同样的时间里,能触达更多客户。

五、发信策略收紧:别让客户看到错误的发件人

之前 send_email 有”个人 SMTP 优先、全局 SMTP 兜底”的逻辑。问题是:如果全局 SMTP 兜底了,客户会收到一封发件人不是业务员的邮件——在外贸里,这会让客户瞬间失去信任(“你是谁?”).

v0.7.2 收紧策略:send_email 只走员工个人 SMTP,移除全局 SMTP 回退。并加了端口推断:465 用隐式 SSL,其余端口用 STARTTLS。

宁可发不出,也不能用一个”错误的身份”发出邮件。信任是外贸的第一资产。

六、其它工程修正

  • 补全缓存 7 天:单公司联系方式按 place_id/website 缓存 7 天,获客重跑不重复爬官网(搜索缓存仍 1 小时)
  • API key 前缀兼容:修复种子 key(8 位前缀)与新建 key(12 位前缀)不一致导致的 401,客户页不再超时
  • 测试扩充:v0.7.2 一次新增 35 条用例,覆盖记忆、摘要、上下文注入、campaign 流水线(当前共 559 条)

七、一点反思

1. 记忆本身还没有压缩。 对话有滚动摘要,但 key_requirements 是纯增量累积——一个长期客户聊一年,记忆 blob 会越来越长。下一步计划:对记忆本身做摘要折叠,或者只注入”最近 N 条 + 摘要”。

2. 记忆系统只是”全流程信息跟踪”的第一块砖。 现在存的是”提炼后的核心需求一句话”,不是”完整来往邮件 + 图向量”。真正完整的形态——邮件归档、图向量化、LLM 自动综合回复、复杂任务转交、Agent 自进化——还在路线图里。这条路还很长,但至少,第一步迈出去了。

这是系列第八篇,也是继第四篇《为什么不用 LangChain 和 MCP》之后又一篇非迭代的个人理解类文章。前几篇都在记”我加了什么”,这篇反过来,讲一个我做了几个月 Agent 系统之后才真正想清楚的概念问题:工作流和 Agent 智能体,到底有什么区别和联系。 不空谈定义,只讲我在自己系统里摸到的东西。 一、先给它们一个朴素的画像工作流(Workflow):开发者把步骤预先排好,每一步做什么、失败了往哪走,都写在代码里。程序沿着这条图一路执行,不问你任何问题。 Agent 智能体:没有预先排好的图。模型在一个”读状态 → 决定下一步 → 执行 → 看结果”的循环里,自己决定往哪走。它走的路是运行时才生成的。 一个类比: 工作流是铁轨上的列车。轨道铺好,到站就停,晚点了也有调度表。 Agent 是没路的越野车。没有轨道,靠当前的地形(上下文)判断往哪个方向开,开错了还能倒回来。 这个类比有个准确的推论:列车不敢开进没铺轨的地方,越野车也没有”准点到达”这一说。 二、区别:控制权在谁手里,代价就是什么把两者摆开,区别其实只有一句话:控制权在开发者手里,还是在模型手里。 其...
