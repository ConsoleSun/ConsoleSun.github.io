为什么不用 LangChain 和 MCP:外贸 Agent 的技术选型与取舍

发表于2026-08-04|更新于2026-08-06|技术
|浏览量:

这是系列第四篇。前几篇讲了整体框架、客户记忆、邮件归档,这篇回答一个绕不开的问题:为什么你的技术栈看起来不主流? 不用 LangChain、不用 MCP、选了图+向量混合检索——不是标新立异,是评估之后的取舍。这篇把三条选择的完整理由写清楚。

一、选型的原则:为约束做选择,不为潮流做选择

我的判断标准只有一条:

一项技术的价值 = 它解决的问题 ÷ 它带来的成本,并且必须在自己项目的约束下衡量。

通用场景下的”好技术”,换到自己的约束下可能是”贵技术”。所以这篇不讲”哪个框架强”,只讲”在我的约束下,为什么这样选”。

我的约束是什么:

  • 单服务、单语言(Python)、单租户
  • 18 个工具全部自有,不依赖第三方集成生态
  • 单一模型(DeepSeek),前缀缓存计费,消息结构直接决定成本
  • 核心链路对延迟敏感,对可控性敏感

二、为什么不用 LangChain

LangChain 解决的问题,不是我的问题

LangChain 的核心价值是广度:500+ 集成、统一抽象、快速接入一切。但我的系统只对接有限的几样——邮箱、ERP、Google Places、Milvus、LightRAG、钉钉,且全部是自己实现的工具。集成生态对我的价值是零,为它付抽象层的成本不划算。

我需要控制的,恰恰是框架抽象掉的

三个具体的设计,是直接决定系统成败的,而它们都要求”越过框架”才能做:

1. KV 缓存优化的消息结构。 四层上下文、动态内容全部折进用户消息末尾、前缀恒定命中 DeepSeek 前缀缓存。ChatMemory 会按自己的格式重排消息——在它里面做缓存优化,是在跟框架打架。

2. 工具网关五步管线。 熔断、权限、执行、校验、修正。框架的 Agent Executor 没有内建的熔断和权限概念,没有”同工具最多重试 2 次的失败修正”——这些照样要自己写。

3. 视角状态机。 双角色视角切换、动态 RAG 权重——框架里没有这个概念。

框架抽象掉的,正是我要控制的;框架给我的,是我用不上的。

排障的透明度

LLM 系统有一个特性:非确定性。出问题时,需要看到原始请求和响应。直接调 SDK,请求响应是什么样,看到的就是什么样;隔着一层框架,要先确认是不是框架的封装改了行为,再排查模型问题——多一层包装,多一层未知。

什么时候我会用

快速原型、重度依赖集成生态、团队协作需要统一约定、非核心链路。这些场景里 LangChain 是正确选择,我只是不在这些场景里。

三、为什么不用 MCP

MCP 卖的是互操作,我的部署里互操作需求为零

MCP(Model Context Protocol)解决的是:让我的 Agent 能用别人写的工具,让我的工具能被别人的应用用。这是协议层的价值。

但我的部署是一个 FastAPI 服务、一门语言、18 个全部自有的工具、单租户——没有外部工具提供商要接,没有别的应用要消费我的工具。为一个不存在的需求付协议层的成本,不划算。

协议给不了的,正是我最看重的

MCP 标准化的是”工具怎么被调用、结果怎么返回”。但它不提供应用层的三样保证:

  • 熔断(连续失败 60 秒冷却)
  • 权限(RBAC + 参数级规则)
  • 校验与失败修正(同工具最多 2 次)

这三样必须写在应用层。就算上了 MCP,网关该写的还是一行不少——得到的只是多一层序列化和进程边界,失去的是进程内直接调用(零 IPC、零网络跳、零序列化)。

我没有拒绝 MCP,只是没走协议层

我的工具注册表已经把规格和实现分离:@tool() 装饰器声明 name / description / JSON schema(和 MCP 的 tool definition 是同一套 schema 语言),权限规则挂在注册表上,执行是独立异步函数。

将来如果出现互操作需求(公司其他 AI 应用要复用工具、团队扩张),包一层适配器就能把注册表暴露成 MCP server——18 个工具一行不用改。规格层已经对齐,缺的只是传输层。

什么时候我会用

公司有多个 AI 应用需要共享同一套工具、需要接第三方工具服务商、团队跨语言协作。这些场景出现时,MCP 是正确答案,迁移路径已经备好。

四、为什么选图+向量混合检索

数据形态决定技术

业务知识库里的信息不是扁平的文档,而是关系:产品 → 规格 → 应用场景 → 客户偏好 → 历史成交。向量检索擅长”语义相似”,但多跳关联(这家客户之前对哪类产品感兴趣、和哪个市场重合)需要图结构。

所以选了 LightRAG(图增强检索)+ Neo4j(图数据库)+ Milvus(向量)的混合方案。LightRAG 本身是成熟的开源项目,不是自研轮子——用它的原因是:图+向量混合是 RAG 的主流进化方向,且它把两种检索的编排成本降到了可维护的程度。

五个知识库,各司其职

知识库 承载内容
业务库 产品、报价、FAQ、行业知识
技术库 工艺、材质、质量标准
管理库 制度、人事、流程
开发信库 8000+ 封爆款邮件模板与话术
客户历史库 开发信全文、客户回信、公司画像

五个库用视角状态机动态分配检索权重,对客户视角和内部视角差异化检索。

诚实的一部分

图+向量对比纯向量,提升幅度我还欠一组量化数据。 选择在设计层面成立(数据形态确实需要关系检索),但”图到底多带来了多少召回提升”没有 A/B 过。这是这条选型里唯一没有补齐的证明,也是下一步要做的事。

五、选型的三条检验标准

把这次选型的判断方法沉淀下来,供以后的项目复用:

1. 它解决的是不是我的问题。 集成生态、互操作、通用记忆——这些是好东西,但不是我的约束下的问题。

2. 它带来的成本我付不付得起。 抽象层的排障成本、协议层的运维成本、框架升级的供应链风险——每一项都要用真金白银的维护时间付。

3. 选择是否有迁移路径。 不用 MCP,但注册表在规格层对齐 MCP;不用框架,但薄库(SDK、httpx、FastAPI)是随时可换的。所有”不用”都留了”要用时怎么接”的答案。

结语

技术选型没有”正确”只有”适配”。偏离主流不是问题,问题是为什么偏离——答得出来,是取舍;答不出来,是跟风。

这个项目的技术栈看起来不主流,但每一条选择都对应一个具体的约束,每一条”不用”都留了迁移路径。选择为约束服务,举证责任在自己——这句话,是这次选型最大的收获。
