把屎山推倒的那天:外贸智能体 v0.9.0 技术债清偿与 Facebook 发帖

发表于2026-08-06|更新于2026-08-06|技术
|浏览量:

这是系列第六篇。前五篇都在讲”加了什么”:客户记忆、邮件归档、钉钉指挥、写信叙事化。这一篇反过来,讲 v0.9.0 这版几乎没加什么,却可能是迭代以来最重的一次——把欠的债还了,把最重的几座屎山推了。顺带,第 18 个工具上线:Facebook 自动发帖——它同时是系统第一次通过工具给纯文本推理模型补上视觉能力。

一、为什么专门腾一版还债

功能加得越快,欠的债越多。v0.8.3 之前,系统的体检结果(已沉淀为 docs/DEBT.md)暴露了三类问题:

  • 会咬人的:硬编码的 ERP token、可打内网的 SSRF、跨客户记忆污染、弱默认凭据
  • 行为分叉的:流式和非流式两套 ReAct 循环各写一遍,连”修正超限”的语义都不一致
  • 维护摩擦的:config.py 变成 397 行的垃圾场,prompt、公司文案、邮件模板全塞在里面

这一版的目标不是功能,是把地基补到能支撑下一层功能。

一个直观的信号:这一版的代码总量在变少——config.py 从 397 行降到 254 行,api/main.py 从近千行拆到 536 行,而工具数从 13 涨到 18。功能在加、代码在减,这是结构变健康的标志。

二、工具从 13 到 18

v0.8.x 到 v0.9.0,工具注册表从 13 涨到 18。完整清单按类别:

类别 工具
知识库检索 search_business / search_tech / search_mgmt / search_outreach / search_customer_history
联网 search_web / web_fetch
视觉 visual_search
产品 get_product_detail
邮件 send_email / check_inbox
记忆 get_customer_memory
执行/存储 sync_to_erp / save_file
获客 lead_mining / campaign_status
对外通道 send_dingtalk_notify / post_to_facebook

近几版确认新增的有三个:search_customer_history(v0.8.1 客户开发历史库)、send_dingtalk_notify(v0.8.3 钉钉告警)、post_to_facebook(v0.9.0,今天)。权限结构不变但数字更新:customer 5 个工具(只读感知类),staff / admin 18 个全量。新增工具全部走同一条网关管线,自动获得熔断、权限、校验、失败修正——这是最初把”安全做进管线而非散落 if”的设计红利,后面每加一个工具都不用重新考虑安全问题。

三、先堵会咬人的洞

安全修复是这版优先级最高的事,挑四个最有代表性的:

1. 硬编码的 ERP token 从代码里消失。 之前 erp_prospect.py 里躺着一个真实的生产 token,进了代码库就进了 git 历史,抹不掉。现在只从 ERP_TOKEN 环境变量读,缺失直接拒绝同步。真实凭据不进代码库,是底线。

2. 知识库管理端口的 SSRF。 /api/admin/datasets/{port}/... 对未知端口会回退 http://localhost:{port}——等于给攻击者一个带内部密钥的内网探测器。现在只认 5 个注册过的知识库 id,其余一律 400,连 URL 都不构造。

3. 跨客户记忆污染。 共享账号(匿名 API key)之前信任客户端传来的 email,客户端可以拿别人的邮箱,读写对方的永久记忆档案。现在记忆主键以服务端身份为准,共享账号剥离客户端 email、按 session 隔离。“你是谁”只能由认证说了算,不能由请求体说了算。

4. 弱默认凭据 fail-fast。 JWT_SECRET 等密钥之前有 changeme-* 之类的默认值,忘了配 .env 就带着已知密钥上线。现在启动时强制校验,缺失直接拒启动——宁可起不来,不带着空门跑。

四、推倒屎山

这是这一版的主体。四座山,一座一座推:

config.py:397 → 254。 system prompt(130 行)搬到 agent/prompts/,公司身份文案搬到 agent/content/company_facts.py,邮件模板搬到 agent/templates/,角色配置搬到 agent/roles.py。config 只留基础设施和兼容转发。改一处不再漏三处——之前公司的主营、产能、认证写在同一批内容里,客服、员工、开发信三端各一份,改一个忘两个。

api/main.py:近千行 → 536。 38 个资源路由拆进 api/routers/ 下的 7 个资源模块(sessions / inbox / drafts / campaign / knowledge / images / visual),认证路由原本就在 auth/ 下,main 只留 chat 两个最重的 handler。单个文件短了,定位问题从”滚几百行找函数”变成”直接进对应模块”。

loop.py:200+ 行的 god function 拆成 3 个模块。 滚动摘要折叠家族抽到 agent/harness/digest.py,意图/视角分析抽到 intent.py,会话级 FSM 存储抽到 session_fsm_store.py。同时修了一批正确性问题:修正超限后补了 return(之前是”假终止”,同一失败工具会一直耗到步数上限)、流式并行工具调用全部执行(之前只执行 index 0)、流式出异常发 error 事件而不是静默掐断 SSE。

死代码与魔法值。 删了 4 处死代码(无人引用的 all_specs、废弃的配额函数等)和 13 个未用 import;Milvus 的 IP、docker 主机名、LLM 超时这些散落三处的魔法数收敛成 config 常量,改地址只改一处。

五、唯一的新功能:Facebook 自动发帖

还债之外,今天的功能面只有一个,给运营部门用:post_to_facebook。

但这一功能还有另一层,可能比”自动发帖”本身更重要:它是系统第一次通过工具,给纯文本推理模型补上视觉能力。

系统的推理底座是 DeepSeek——纯文本模型,读不了图。之前客户发来一张产品图,系统只能做”以图搜图”(图像向量化后在 Milvus 里比相似度),模型并不理解图里画的是什么。这次的解法不是把底座换成多模态模型,而是把”看图”做成一个工具:

这个设计让三件事同时成立:

1. 推理模型保持纯文本,不动底座。 换多模态底座,会动到 KV 缓存纪律、成本、延迟这一套已经调好的东西。现在 DeepSeek 依然是唯一的大脑,图片理解这件它不擅长的事,外包给擅长它的本地模型。

2. 视觉能力可插拔。 调的是本地 Ollama 的 qwen3-vl:8b,由 FB_VLM_MODEL 一个配置项决定——想换别的多模态模型,改配置,不动 Agent 逻辑。

3. 图片不出内网。 多模态调用走本机 Ollama,产品图是公司资产,不送到外部服务。对”图库即机密”的场景,数据不出门本身就是价值。

降级链则保证视觉能力是”可降级的增强”,不是硬依赖:

  1. 没配 FB_PAGE_ID / FB_PAGE_ACCESS_TOKEN → 退回文案生成器:VLM 照常生成文案,返回给员工复制,人工发布
  2. VLM 调用失败 → 回退默认文案模板(需求 + 固定标签)
  3. 发布失败 → 返回错误信息 + 文案预览,仍然能手动补救
  4. 传了 custom_text → 跳过 VLM,直接发自定义文案

一条纪律延续了下来:外围功能可以坏,不能拉着核心链路一起死。 钉钉、Facebook、邮件——每个对外集成都按”不可用时要优雅降级”来写。

回看系列第一篇那句话:LLM 是大脑、上下文是眼睛、工具是手脚。 post_to_facebook 给这句话补了一层新的意思——工具不仅能”动手”,也能”看”。模型不会的能力,不一定要换模型,可以做成工具挂上去。以后凡是”模型本身不会、但工具能替它感知”的能力,都能用同一个模式接入。

权限上,post_to_facebook 只对 staff/admin 开放——涉及公司官方账号的操作,不给客户侧留入口。

六、立规矩

这版最容易被忽略的产出是 docs/change-checklist.md——把踩过的坑固化成规则:

  • 改行为 = 配置 / 代码 / 文档三处同步(公司文案改源模块,不改转发值)
  • 状态字符串先枚举化再动状态机("pending"/"running" 这类裸串在 6+ 个文件里流转,改一处漏一处是常事)
  • 不可信输入不得构造记忆键(消息正文、请求体字段、IMAP From 头——全部不信)
  • 测试打在实际消费符号的命名空间(路由拆走后,monkeypatch 的目标模块也变了)

规则的价值不在这一版,在下一个要改这些文件的人——那个人大概率是我自己。

结语

v0.9.0 的意义不是”加了什么”,而是”拆了什么、堵了什么”。工具从 13 走到 18,代码却在变少,说明系统的重心在从”铺功能”转向”管复杂度”。

距离 v1.0 还有三件事一直没动:全流程信息跟踪、复杂任务转交、Agent 自进化。它们都需要这版打下的地基——记忆键不乱、路由找得到、循环不分叉,下一步才敢往上盖。
