工作流与 Agent 智能体:区别、联系,与一条合流的河

发表于2026-08-09|更新于2026-08-09|技术
|浏览量:

这是系列第八篇,也是继第四篇《为什么不用 LangChain 和 MCP》之后又一篇非迭代的个人理解类文章。前几篇都在记”我加了什么”,这篇反过来,讲一个我做了几个月 Agent 系统之后才真正想清楚的概念问题:工作流和 Agent 智能体,到底有什么区别和联系。 不空谈定义,只讲我在自己系统里摸到的东西。

一、先给它们一个朴素的画像

工作流(Workflow):开发者把步骤预先排好,每一步做什么、失败了往哪走,都写在代码里。程序沿着这条图一路执行,不问你任何问题。

Agent 智能体:没有预先排好的图。模型在一个”读状态 → 决定下一步 → 执行 → 看结果”的循环里,自己决定往哪走。它走的路是运行时才生成的。

一个类比:

  • 工作流是铁轨上的列车。轨道铺好,到站就停,晚点了也有调度表。
  • Agent 是没路的越野车。没有轨道,靠当前的地形(上下文)判断往哪个方向开,开错了还能倒回来。

这个类比有个准确的推论:列车不敢开进没铺轨的地方,越野车也没有”准点到达”这一说。

二、区别:控制权在谁手里,代价就是什么

把两者摆开,区别其实只有一句话:控制权在开发者手里,还是在模型手里。 其它所有差异都是这句话的后果。

维度 工作流 Agent
路径 预定义,写死在代码里 运行时由模型生成
可预测性 高,同输入同输出,可测试 低,同输入不一定同输出
成本 确定性执行,几乎为零 每一步决策都是一次 LLM 调用,随步数线性涨
失败模式 可枚举,出错好定位 不可枚举,出错难复现
灵活度 低,想加一步要改代码 高,加一个能力 = 加一个工具
适用场景 路径清晰、要求稳定 路径开放、要求灵活

这里面最容易被忽略的是成本。工作流每一步是代码,Agent 每一步是模型调用。同样跑完一个任务,工作流的边际成本趋近于零,Agent 的成本随决策次数线性增长。所以”能用工作流就不用 Agent”不是保守,是省钱——这个项目跑在按 token 计费的 DeepSeek 上,成本是每天都要面对的真实约束。

三、联系:一个 Agent 系统里,大部分代码其实是工作流

这是我做这个系统最大的一个认识转变:

真正跑在生产里的 Agent,不是”模型一路推理到结尾”,而是”模型只在一个个决策点介入,中间全是确定性工作流”。

拿我自己的系统举例,每一块都能对上:

1. 工具网关:包在每个决策点外面的工作流。 每次工具调用,都要先过一遍”熔断 → 权限 → 执行 → 校验 → 修正”五步管线。这五步全是代码,不是模型。模型只负责两件事:决定调哪个工具、传什么参数。剩下的是工作流。

2. 全自动获客:一条重工作流,只有一步是 LLM。 后台一键 → 按配置逐国找客户 → 已联系邮箱/域名去重 → 起草开发信 → 员工 SMTP 限速发送 → 自动同步 ERP。这一整条流水线里,只有”起草开发信”是模型干的,其余全是确定性的代码步骤。Agent 的自主性只体现在”顺着这条线往下走”。

3. v0.9.1 的 compile_b2b_markdown_to_html:一次主动往工作流方向的回退。 让 Agent 写官网文章时,我没有让模型直接吐 HTML,而是让它只输出干净的 Markdown,再由编译器按设计系统生成页面。排版是确定性任务,本来可以让模型干,但把它拿回来交给代码,更稳、更省、更可测。这是”确定性任务,能拿走就从模型手里拿走”的一个典型动作。

4. Facebook 发帖的四级降级链:工作流式的兜底。 缺页凭据 → 退回文案生成器,文案给员工人工发布;VLM 识别失败 → 回退默认文案模板;发布失败 → 返回错误信息和文案预览供手动补救;传了自定义文案 → 直接跳过 VLM 发送。这四级降级全是代码写的规则,保证”外围功能可以坏,核心链路不能跟着死”。

所以我的结论是:工作流和 Agent 不是二选一,而是分层。 工作流是骨架,LLM 是决策器官,Agent 是这一整具躯体。一个健康的 Agent 系统,是”工作流为体、LLM 为脑”——骨架撑起躯干,大脑发号施令,手脚执行动作,缺一块都不完整。

四、怎么判断该用哪个

一个朴素的标准:任务的路径,你知道怎么走吗?

  • 知道,而且每一步都说得清 → 工作流。
  • 不知道,但你能描述”该怎么判断” → Agent,让模型来做那个判断。

但更准确的答案是:几乎总是混合。 把稳定的部分做成工作流,把需要判断的部分留给模型。原则就是上面那句:确定性任务,能拿走就从模型手里拿走。每拿走一块,系统就便宜一点、稳定一点、可测一点。

这里有一个可以拿来检验任何”Agent 系统”的方法:

把系统里的 LLM 调用全停掉,看看还剩什么。
剩下的还能跑通一个任务 → 你写的主要是工作流,Agent 是点缀。
一停就瘫 → 你是真的依赖模型判断。

这个检验很实用。市面上很多号称”Agent”的产品,其实是”披着 Agent 皮的工作流”;也有很多真正需要判断的环节,被人硬编码成了死板的工作流。区分它们,不是看宣传文案,是看控制权实际在哪里。

五、诚实的一部分

有几点我不藏着:

1. 我自己的系统也在滑动。 获客那段是重工作流,对话那段是重 Agent。这不是设计出来的,是问题逼出来的——凡是路径清楚的环节,写着写着就变成工作流了;凡是必须临场判断的,硬做成工作流就做不动。

2. “Agent 化”不是越高越好。 把确定性任务交给模型,不是更智能,是更贵、更不可靠。我见过为了”更 Agent”而把一段稳定的规则流程改成模型调用,结果每次都要为它的随机输出兜底。

3. 过度工作流化也有代价。 一个环节的判断写死错了,整条线就跟着错,还很难发现。真正健康的系统,是承认”判断”和”执行”是两件事,让模型判断、让代码执行。

结语

工作流和 Agent 不是竞争对手,是分工:工作流负责把既定的路走对,Agent 里的大脑(LLM)负责在岔路口选择。 判断交给模型,执行交给代码——这不是妥协,是工程上唯一走得通的路。

回到系列第一篇那句话:LLM 是大脑,上下文是眼睛,工具是手脚。这句话不需要再补一层”神经线”——更准确的理解是:工作流就藏在工具层里面,它就是工具层的内部结构。 手脚从来不是一根根孤立的手指,而是由很多小关节复合而成的:Agent 的每个工具,内部往往就是一段工作流。lead_mining 是整条获客流水线,publish_wp_article 是”撰写+编译+发布”,post_to_facebook 是”识图+四级降级+两段式发布”。所谓工作流,是工具层怎么被组织起来;所谓 Agent,是”大脑 + 眼睛 + 手脚”这一整具躯体。决定调哪只”手”的是大脑——LLM。两者本就是一体的。
