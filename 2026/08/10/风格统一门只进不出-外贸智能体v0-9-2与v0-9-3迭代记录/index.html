风格统一,门只进不出:外贸智能体 v0.9.2/v0.9.3 迭代记录

发表于2026-08-10|更新于2026-08-10|技术
|浏览量:

这是系列第九篇,也是第一篇同时记录两个版本的文章。v0.9.1 让 Agent 会写官网文章,但”会写”和”写得像公司的文章”之间还有一段路。v0.9.2 把这段路走完:把排版编译器重构成风格令牌驱动,让 LLM 产出的每一篇官网文章都长成一个样。v0.9.3 打开一扇门:接入了出站 MCP 客户端管道,但这扇门只进不出。一个往内,一个往外,都值得单独讲。

一、风格令牌化:让”风格统一”成为结构,而不是约定

1. 上一版留下的问题

v0.9.1 的设计是:LLM 只输出干净的 Markdown,后台编译器按公司设计系统生成 HTML。这一版把”排版”从 LLM 手里拿走了——排版从此是确定性任务,由代码完成。

但 v0.9.1 只有一个风格(b2b 棕色企业风),编译器是写死的单套逻辑。问题来了:要加 guide 风格怎么办? 复制一套编译器改颜色?那就回到两套重复代码——v0.9.0 刚还完”改一处漏三处”的债,不能又欠回去。

2. 重构:风格变成数据

v0.9.2 的做法是风格令牌化:

风格不再散落在编译器代码里,而是收敛成一份令牌配置。色板、标题样式、表格表头、TOC 卡片、CTA 区块——全部是数据。b2b 是棕色企业风(零加粗),guide 是 teal 选购指南风(支持加粗、有序列表、产品图)。加第三种风格,只需要再写一份 token 配置,解析器和构建器一行不用改。

3. 这个设计真正精妙的地方

风格令牌化的收益,不止是”代码好维护了”。它回答了一个更根本的问题:怎么让 LLM 固定产出模板风格完全统一的网页?

答案是:把 LLM 的输出空间限制在”语义标记”这一层。 它只能从我们选定的模板小块中拿部件——写 ## 标题、写表格、写图片 alt 的 | left/right 标记。样式、颜色、布局、TOC 结构、CTA 区块,它一个都碰不到,全是代码按令牌渲染的。

于是”风格统一”不是”LLM 很听话”,而是”LLM 没有机会不统一”。约束的是接口,不是想象力。

而另一面同样重要:写作能力最大限度还给 LLM。 每篇文章的选题、论点、正文、措辞,完全由模型自由生成,不套任何内容模板。外部风格相同,核心内容不模板化——这两件事各归其位:风格统一是品牌资产,内容差异化是 SEO 资产。

4. 顺带解决的两个问题

这一版还带了两件事:

图片压缩修复大图上传超时。 上传前 Pillow 自动压缩(长边 ≤1600px、JPEG 质量 80 / PNG optimize),实测上传体积减小 89%。以前产品实拍图直接传,大图经常超时;现在压缩后才进 WordPress 媒体库。

_IMAGE_DIMS 真实方向缓存。 上传成功时用 Pillow 读取图片真实尺寸缓存起来,编译器据此自动判定横竖方向——竖图 220px 左右混排垂直居中、横图整幅展示、正方形尊重显式标记。关键在顺序:真实方向优先于 LLM 标记——LLM 写错 alt 标记也不怕,方向以图片事实为准。

二、MCP:从”不用”到”有选择地用”

1. 为什么当初不用(回顾第四篇)

系列第四篇《为什么不用 LangChain 和 MCP》写过一个判断:MCP 卖的是互操作,而我的系统是单服务、单语言、单租户、18 个全部自有的工具——没有外部工具提供商要接,没有别的应用要消费我的工具。为一个不存在的需求付协议层的成本,不划算。

2. 什么变了:开发速度成了真实需求

v0.9.3 为什么开始接 MCP?因为需求出现了:开发速度。 后续要接外部能力时,与其从零实现每一个服务的客户端(认证、限速、重试、超时),不如直接接现成的 MCP server——生态里成熟的能力,接进来就是工具。这是为效率付费,是第四篇说的”为约束做选择”里的新约束。

3. 有选择地用:门只进不出

这是最重要的一句:MCP 这个门,只做入口,不做出口。

  • 入口(出站 Client):把外部 MCP server 接进来,注册成 mcp_<server>_<tool> 普通工具。这是提高开发速度的方向。
  • 出口(把自己暴露成 MCP server):不做。公司内部工具——发邮件、写 ERP、查客户记忆、官网发布——如果暴露成 MCP server,等于把内部能力开放给外部。公司信息泄露是底线,这条线不碰。

所以”用 MCP”和”有选择地用 MCP”是两回事:入口是效率,出口是安全,两个方向分开判断。

4. 入口的实现要点

  • MCP_SERVERS 单行 JSON 配置驱动(字段 name/url/token/tools),lifespan 启动时连接白名单的 Streamable HTTP server
  • 外部工具静态注册为普通工具,staff/admin 可见,customer 不可见;对 LLM 和网关与内部工具无差别——自动获得角色过滤、ToolGateway 五步管线、观测计数,零改动 loop/gateway/context
  • per-server 熔断隔离:复用 BreakerState(3 次/60s),但只计 transport 异常——外部 server 故障不污染全局熔断器
  • 外部结果视为不可信:回填前过 filter_input 防提示注入,统一加 [external:<server>] 来源标记(过滤之后再加,避免标记本身误触发),结果截断上限 4000 字符
  • 空配置 = 功能关闭零影响;坏 JSON 安全降级空列表;单 server 连接失败只告警不阻断启动

5. 诚实的部分

MCP 目前还没接任何真实服务。 这一版是能力就位、服务待接——管道、熔断、注入防护、来源标记都铺好了,但 MCP_SERVERS 还是空配置。接什么服务、什么时候接,等下一个真实需求出现。这也是为什么这一版敢叫”门只进不出”:门先装好,开多大、往哪开,由需求和安全边界共同决定。

三、数字

  • 测试:773(v0.9.1)→ 782(v0.9.2,+9:压缩/方向布局/guide 风格/官网外链)→ 809(v0.9.3,+27:MCP 配置解析 9 条 + client manager 18 条),默认测试集全绿
  • 工具注册表:23 个内部工具不变;MCP 工具按配置动态注册,当前为 0(未接服务)
  • 图片上传体积:实测 JPEG -89%
  • 工具超时统一 ≥60s:web_search/places/erp/product/facebook/web_fetch/customer_history/lead_mining/browser/wp 全线,发布保持 90s;快路径(SMTP/IMAP 连接、DoH 查询)保持秒级不拉长

结语

v0.9.2 和 v0.9.3,一个往内,一个往外。

往内:把”风格”从模型手里彻底拿走,变成代码资产。LLM 从模板小块中拿部件,风格就永远统一;写作能力还给 LLM,内容就永远不模板化。

往外:给外部工具开一扇只进不出的门。入口为效率,出口守底线。MCP 从”不用”到”有选择地用”,不是推翻了第四篇的判断,而是约束变了——第四篇说”为约束做选择”,这一版的选择依然是这句话的答案。

但这两版真正的意义,不在两个功能,而在于一条线——harness。回头看整个系统:工具网关五步管线是 harness(把每次工具调用包进熔断/权限/校验/修正),滚动摘要和 KV 缓存纪律是 harness(把上下文包进可控边界),_safe_parse_json_args 是 harness(把截断风险包进解析层),风格令牌化也是 harness(把输出包进接口约束)。所谓 harness,就是把模型包进一整套工具、约束和流程里,让一个不完美的模型在不可控的环境里稳定办成事。这个系统从头到尾做的都是同一件事:给不确定性套上可信边界,让模型在边界内自由发挥。 约束的是接口,不是想象力——合适的约束不是压缩能力,是让 LLM 更好地为人所用。这句话,是这两版最想说的,也是这个系统最想说的。

回到系列第一篇那句话:LLM 是大脑、上下文是眼睛、工具是手脚。这两版都在打磨手脚:一副手脚学会了按令牌干活,一副手脚学会了从门外接东西。大脑还是那个大脑,但能干的事又多了一点。
