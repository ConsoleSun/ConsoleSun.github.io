先落盘,再遗忘:外贸智能体 v0.9.5 迭代记录

发表于2026-08-12|更新于2026-08-12|技术
|浏览量:

这是系列第十一篇。上一篇讲获客,是往外的事;这一篇讲记忆,是往里的事。v0.9.5 干了一件事:把”聊过什么”从内存搬进数据库。以前,Agent 的会话存在 Redis 里——快,但七天后蒸发。今天之后,对话是白纸黑字:重启不丢,换人读不到。

一、会话为什么会丢:一段会被蒸发的记忆

先交代背景。这个系统的对话状态一直存在 Redis:快,支持 KV 缓存纪律,但它是内存数据库——快是它的优点,易失是它的宿命。7 天 TTL 一到,聊过什么就没了;服务器一重启,聊过什么也没了。

客户记忆(v0.7.2)是客户维度的永久存储——客户是谁、买过什么、聊过什么主题,落 PostgreSQL 永久保存。但对话本身不是:客户昨天说”我们下个月要 500ml 的威士忌瓶,有没有带木塞的”,今天 Agent 重启,这句话就没了,客户得再讲一遍。

对一个做关系生意的系统来说,这是不能接受的。上一篇说过:外贸是关系生意。关系的载体是什么?是对话。对话会蒸发,关系就没有连续性——Agent 记不得客户上次说到哪,就像业务员一离职,客户的一切都要重来。

二、迁移:Redis 退居二线,PostgreSQL 成为唯一真源

v0.9.5 把会话、消息、滚动摘要、邮箱绑定全部落盘 PostgreSQL(0 TTL),Redis 退为 L1 缓存——未命中自动回填,速度不降,持久性有了。这是”缓存 + 真源”的标准形态:缓存负责快,真源负责在。

三个细节值得单独说:

复合主键 (user_id, session_id)。 以前 session_id 是全局唯一的,如果两个账号恰好复用同一个 session_id,理论上能读到对方的会话——审计时发现这个隐患,这次用复合主键根治:会话永远挂在”谁的”名下。跨账号读他人会话,在存储层就写死了不可能。对一个内部系统来说,这条比功能更重要。

先落盘,再遗忘。 滚动摘要是这个系统的核心机制:对话超过 20 轮,窗口外最老的一段折叠成摘要。以前是先折叠再存,如果这时候 Redis 挂了,折叠段就永久丢了——丢了就是真的丢了,找不回来。这版改了顺序:先落盘,再折叠。PG 写失败就抛异常,绝不裁剪。机器的遗忘应该是”算了”,不能是”丢了”。

懒补建表 + 自动迁移。 修复启动竞态(表还没建好就被访问);旧 schema(单列主键 + role 死列)自动迁移;建池加锁单例。

三、上线安全加固:一揽子

  • JWT:弱密钥黑名单 + 最小长度硬校验,密钥已轮换(真实密钥只在 .env,不进代码库——v0.9.1 立过的规矩,这次又守了一遍)
  • 生产默认关闭 /docs /openapi.json——API 文档是攻击者的地图,内部系统不需要公开地图
  • /drawings 图纸接口加鉴权——图纸是公司的资产,不是公共资源
  • /auth/login 失败锁定——防爆破
  • CI 只注入最少必需密钥

四、迁移的坑:旧会话消失了

上线后发现一个问题:用户以前的会话从列表里消失了。

根因很清楚:列表接口改成了只读 PG,但旧会话还在 Redis 里——搬家搬完了,新家没有旧东西,旧家又没人去看了。更糟的是,Redis 有 7 天 TTL,不处理的话,旧会话会随逐出永久消失。

修复分两层:

  • 启动时回填:lifespan 启动时把 Redis 中未落盘的会话幂等回填到 PG(复用 save_session 事务写,不产生重复)
  • 列表双源合并:list_sessions 合并 PG + Redis 双源,按 session_id 去重,PG 优先——过渡期两个家都照顾到,双保险防再次断档

生产验证:重启后自动回填 6 条旧会话,列表从 6 恢复至 12,消息完整落 PG。

这个坑的教训:迁移不是”搬完就完”,是”过渡期两个家都要照顾”。新系统上线,旧系统的存量要有人负责搬运,否则用户感知就是”东西丢了”。

五、发布版/开发版双环境

  • 发布版(docker-compose.yml):去掉源码 bind mount,改跑构建镜像——发布不可变可复现,线上跑的就是构建产物
  • 开发版(docker-compose.dev.yml):8101 端口 + 独立 dev 库 + Redis db1,源码热改,守护默认关
  • playwright 浏览器缓存运行时挂载(镜像不内置);pip 走腾讯镜像 + timeout/retries 抗抖动

顺带一个镜像的坑:.dockerignore 之前把 sandbox/ 排除了,但 sandbox/ 是运行时模块(api/main 导入它的 filter/quota)——镜像构建成功、启动崩溃。能在开发环境跑通的代码,发布版不一定能跑——这正是发布版必须跑镜像的原因:问题只在发布形态下暴露。

诚实的部分

  • 越权隐患是审计时发现的,不是设计时发现的——复合主键本该一开始就有
  • 迁移丢会话的坑是生产上线后用户报的——测试覆盖不到”存量数据”这件事,数据迁移的验证要靠真实数据
  • 双环境还在磨合,开发版和发布版的行为差异要慢慢收敛

结语

回到系列第一篇:LLM 是大脑、上下文是眼睛、工具是手脚。今天这版动的是眼睛的存档——上下文从”转瞬即逝”变成”白纸黑字”。

这套系统从头到尾在做同一件事:给不确定性套上可信边界。记忆也一样:模型可以遗忘(滚动摘要折叠),但不能弄丢(先落盘再折叠)。遗忘是能力,丢失是事故——把两者隔开的,就是那一次先落盘。
