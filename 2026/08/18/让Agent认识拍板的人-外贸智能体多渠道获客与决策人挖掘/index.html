让 Agent 认识拍板的人:外贸智能体多渠道获客与决策人挖掘

发表于2026-08-18|更新于2026-08-18|技术
|浏览量:

这是系列第十三篇。第十篇《电商的评分,外贸的信》讲过 v0.9.4 把获客管线切到 Apify 云端——那一次,Agent 学会了"找公司"。这一篇讲同一件事的下一段路:找到公司之后,还要找到公司里那个拍板的人。为了找到这个人,获客的路从一条变成了三条,还多了一位"数据商"朋友。

一、从一条路到三条路

v0.9.4 的获客只有一条路:Google Maps。地图能搜到的是"开在街上"的商家——酒厂、啤酒厂、饮料厂大多在地图上有一席之地,但很多真正的 B2B 买家,尤其是批发商和区域分销商,并不靠地图吃饭。一条路走到底,名单会越来越窄。

这一批把路修成了三条:

  • google_maps:Apify Google Maps Scraper(compass/crawler-google-places),名称/官网/电话/地址/城市/分类/谷歌评分/评价数
  • linkedin:Apify LinkedIn Companies 搜索,名称/官网/规模/行业/领英主页
  • facebook:Apify Facebook Pages 搜索,名称/官网/专页链接/粉丝数

获客设置行从"国家|关键词"升级为"国家|关键词|渠道",渠道填 all 时三路并发搜索、聚合去重。LLM 关键词扩展同步上线:产品词自动扩展成 2-3 个企业类型搜索词——搜 "sake" 会扩展出 "sake brewery / manufacturer",解决"产品词搜到零售店被过滤成 0 结果"的老问题。每个扩展词都走完整渠道。

跨渠道去重要做好,否则多渠道就失去了意义:同一家公司在三个渠道出现是常态,企业名标准化(去标点、去后缀)+ 官网域名归一后合并,只算一次。多渠道的意义是覆盖,不是重复。

二、找到公司之后:决策人深度挖掘

1. 开发信发给谁,是两回事

开发信发给 info@,和发给采购经理,是两个世界。info@ 大概率被淹没在垃圾邮件里;发给对的人,才有回复率。v0.9.4 的官网联系方式补全已经做到 person → role → generic 的邮箱排序,但"这家公司里谁是拍板的人",还是缺的。

2. 四路并发穿透

新的决策人挖掘模块(decision_maker_enricher.py)在拿到公司名单后,四路并发穿透:

  • 👔 LinkedIn 公司主页:在职高管、采购负责人、创始人
  • 📱 WhatsApp 商业直通车:wa.me/ 商业号码与国际电话
  • 📘 Facebook 商业专页:About 简介、公开电话、邮箱
  • 🌐 官网子页:/team、/about-us 等深度页面,找创始人/主酿酒师/采购主管

四路结果汇入统一画像聚合器(Unified Profile Aggregator),输出高保真买家卡片:姓名、职务、邮箱、电话、社交主页,一卡集成。

3. 两个细节:词库与过滤

决策人职务词库支持中英西多语系——客户分布在南美、西班牙语地区时,compras(采购)、dueño(老板)、maestro tequilero(龙舌兰酒大师)这些词一样认。邮箱过滤同样严格:网站模板占位符(you@yourcompany.com 这类)、免费邮箱、Sentry 等埋点追踪地址(24 位以上十六进制哈希前缀)全部剔除,不给开发信发进"黑洞"的机会。

4. 考察期

这个模块标注为考察期实验模块:本地挖掘不花 Apify 配额,但画像质量要靠真实客户验证,不吹效果。

三、Apollo:考察期结束

1. 从锁定到放行

apollo_prospect.py 在仓库里躺了一段时间,一直被 .gitignore 锁着(考察期锁定)。这一批解除锁定,正式注册成两个工具:

  • apollo_search_people:按公司域名/名称 + 职务关键词(procurement / buyer / CEO…),在 Apollo B2B 数据库里搜索决策人名片与邮箱
  • apollo_enrich_contact:按姓名 + 公司域名定向补全、验证邮箱

为什么已经有本地挖掘,还要接 Apollo?因为两者不重复:本地挖掘负责"这家公司公开页面上有什么",Apollo 负责"这家公司谁拍板、邮箱验证过没有"——几亿张联系名片,邮箱带验证状态。一个零成本看运气,一个花钱买确定性,互为补充。

2. 降级要体面

外部 API 的错误处理是这门课的加分项:401 提示 API Key 无效或过期;403 明确告诉用户"Apollo 免费版不支持 REST API 检索,要么升级付费方案,要么继续用零成本的 Apify 渠道";429 提示频控;超时兜底。每一句都是人话,不抛裸异常——这是开发规范里"容错要显式、降级要体面"的规矩,这份实现是范例。

四、数字

  • 获客渠道:1 → 3(google_maps / linkedin / facebook,可 all 并发聚合)
  • 决策人画像来源:4 路(LinkedIn / WhatsApp / Facebook / 官网子页)
  • 工具注册表:23 → 25(新增 apollo_search_people / apollo_enrich_contact)
  • 测试:792 收集(默认套件 783 条全绿 + 9 条真实环境 integration 默认排除)

五、诚实的部分

  • Apollo 免费版实测返回 403:工具就位,真实效果要等账号升级后验证,当前主链路仍是零成本的 Apify 渠道
  • 决策人深度挖掘还是考察期模块,画像质量要靠真实客户校准
  • 多渠道去重依赖企业名/域名的标准化规则,规则是枚举的,新后缀、新命名习惯要持续补
  • 这一批都还在 dev 分支,稳定后会合并 main 发版

结语

回到系列第一篇:LLM 是大脑、上下文是眼睛、工具是手脚。这一版打磨的是手脚里最像销售的那一双——找客户。第十篇让 Agent 学会找公司,这一篇让它学会找公司里那个拍板的人:从广撒网,到精准制导。

外贸获客的本质,从来不是名单的长度,而是名单上的人对不对。给不确定性套上可信边界:找人的不确定性,套上"三渠道交叉 + 四路画像聚合 + 数据商验证"的边界;外部 API 的不确定性,套上"人话降级"的边界。模型还是那个模型,但它认识的人,越来越接近那个真正说了算的人。
